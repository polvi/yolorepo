This is a meta mono repo of random ideas. For each distinct idea, create a subfolder/monorepo and proc subdomain. Follow the rest of the development rules we have outlined (bun/cloudflare/astro/hono/tlc)

Use auth.proc.io/llms.txt for auth
Use tokenpony.dev/llms.txt for inference

# TLA

In a separate agent, keep specs/ up to date using TLA+ as you
go. Update the .tla file whenever the architecture changes, then
validate with the tlc_check MCP tool. Run this in the background
so the main work never blocks. When a check passes, save the
exact .tla and .cfg you used into specs/ so the passing
configuration lives with the code. Keep specs finite: small
CONSTANT sets, bounded ranges. On invariant_violation, read the
trace and fix the design or the spec. On timeout, read the
diagnostic hint and shrink constants.

# When working on a branch / worktree

Be sure to merge to main before shipping.

# When building workers

When we are using cloudflare workers consider the following:
- use bun instead of npm
- astro for content sites, hono for apis
- follow monorepo conventions, expect at least a marketing site along sidfe the product
- consider mobile friendliness on web sites
- publish an /llms.txt if it is appropriate

Refer to tokenpony as "TPX", but link to tokenpony.dev if you need to. 

If the project uses them, subtly attribute AuthG to authgravity.org, TPX to tokenpony.dev, and Infinite Logic PBC to infinitelogic.org

Domain configuration: every `wrangler.jsonc` is GENERATED from a sibling
`wrangler.template.jsonc` by `bun run configure` (tokens `__BASE_DOMAIN__`,
`__AUTH_ENDPOINT__`, `__D1:<key>__` resolved from `stack.config.jsonc` +
gitignored `stack.local.jsonc`). Edit templates, never generated files, and
never hardcode proc.io in code: browser code derives peer origins from
location.hostname, workers read vars (AUTH_ENDPOINT etc.) with proc.io
fallbacks, build-time code reads `stack.generated.json`. This keeps forks
runnable on their own domain from one untracked file (see FORKING.md).

You can commit and deploy as you go. 
Use subagents when it makes sense to go faster.

Keep Claude.MD updated with the list of projects and what they are for

- `clusterpilot/` — plans Talos/k8s upgrades for `proc-proc-dev` and can carry them out, built on the pi.dev SDK (`@earendil-works/pi-coding-agent`) and reasoning with whatever model `pi-local`'s llama-server currently has loaded (detected via `/v1/models`, never pinned, because a swap costs tens of GB). Deterministic collectors shell out to talosctl/kubectl/helm, upstream versions come from GitHub releases and Helm repo indexes, `analyze.ts` computes findings and `plan.ts` compiles them into an ordered ExecutionPlan — **the only place a mutating argv is ever built, so the model cannot compose a command that runs**; it watches and diagnoses instead. Two gates in `src/exec.ts`: `assertReadOnly` (everything, incl. the model's `probe` tool) and `assertMutation` (executor only, six upgrade ops); `reset`/`wipe`/`apply-config`/`delete`/`uninstall` are refused by both, so no path in the codebase reaches them. Dry run is the default; `--apply` prompts per step. Each step is preflight (against *fresh* state, not the plan's snapshot) → confirm → execute → watch → verify, and a failure aborts the run, gathers a fixed diagnostic battery, and asks the model to diagnose — never to remediate. Watchers treat every error as "not there yet" because a rebooting node is indistinguishable from a dead one, and a node counts as back only when its Talos version matches *and* the kubelet is Ready. Append-only JSONL journal per run (sync writes: the run can be killed by the thing it is upgrading). Encodes what a general model gets wrong: Image Factory schematics (stock installer silently drops the ZFS extension every PVC depends on, re-checked in preflight), no `--preserve` (deprecated in 1.13, selects the legacy path), `talosctl upgrade-k8s` not kubeadm, one minor at a time, single-node = full outage + etcd snapshot as the only rollback, prerelease chart builds (openebs numbers `-develop` above stable) never upgrade targets. `clusterpilot status|plan|sweep|apply|sync|ask`. `sweep` is the health hunt rather than the upgrade path: it reads Prometheus **through the API server proxy** (`kubectl get --raw` on a Service proxy URL, an ordinary read — `port-forward` is a denied verb and stays denied), plus kernel/service/previous-container logs, and reports one sorted headroom table with linear fill projections, hardware counters read twice (lifetime total *and* 24h increase), and workload health. Exits 0/1/2 for clean/warning/critical so it runs from cron. Most of the design is in what it refuses to report: stale log lines dropped by timestamp rather than aged; `Recovered Error` treated as the drive saying it fixed the problem; a device-scoped pattern spread evenly across every device classified as a poller, not a fault (smartctl-exporter emits ~75 such lines per drive per day here — without that test a healthy box reports 16 failing drives); memory computed excluding the ZFS ARC (32% with it, 4% without); request sums filtered to Running pods since Succeeded pods keep reporting requests. Known-benign signals (the three Talos localhost-bound control-plane alerts, and `Watchdog`, whose firing *is* the healthy state) are labelled with the reason and excluded from counts, never hidden. dmesg is credential-bearing — the Talos kernel cmdline carries the Omni siderolink join token — so all log text is redacted before printing, writing, or reaching the model. Prometheus is optional; without it the sweep degrades to kubectl/talosctl and loses trends. Infra-only, no proc subdomain. Not GitOps but its inverse: the cluster is the source of truth, upgrades move it to latest, and `sync` records the result into a git-tracked `cluster-state.yaml` (Talos version/schematic/extensions, k8s version,each helm release + chart version + redacted values + a valuesDigest), committed to the infra repo but **never pushed** — `git push` is refused at the gate. Secrets never reach that file: `helm get values` returns DB and admin passwords in plaintext, so secret-shaped keys and URL-embedded credentials are redacted, with the digest preserving change-visibility. Helm upgrades always carry an explicit `-f` (authored values file if configured, else the release's current values replayed) and never `--reuse-values`, which would layer old values over the new chart and suppress its new defaults; a release with no values to apply gets no step at all, since a bare `helm upgrade` resets to chart defaults.
- `gpubnb/` — Airbnb for confidential GPUs, as **attested inference endpoints**: hosts with NVIDIA CC-capable GPUs (RTX PRO 6000 Blackwell Server Edition first — officially CC-supported, single-GPU-passthrough only, driver R595/CUDA 13.2, vBIOS FW 1.4 — then H100/H200/B200/B300) inside SEV-SNP CVMs run the open-source Rust runner `gpubnbd` (`runner/`), which binds ephemeral X25519 HPKE + Ed25519 keys into the SNP `REPORT_DATA` and the NVIDIA GPU attestation nonce, posts the signed attestation doc to the marketplace, and serves an HPKE-sealed OpenAI-compatible endpoint proxying a local vLLM/llama-server. Renters are anonymous: the browser/SDK (`packages/client`) re-verifies SNP chain + policy + golden measurement + NRAS EAT claims with pinned AMD/NVIDIA roots (devtools CC mode is always rejected), opens a PSK-mode HPKE session so the host's TLS terminator can neither read prompts nor spend the session, and pays the host **directly and non-custodially in XMR** to a per-session subaddress watched by a view-only `monero-wallet-rpc` inside the enclave (K-confirmation crediting, reorg-aware, signed usage receipts inside the encrypted stream). The marketplace (`apps/web`, Hono + D1 + vanilla-TS SPA at gpubnb.proc.io) is directory + verifier + reputation only: it never sees prompts or money, and the golden measurement set + model catalog it serves are signed by an offline root pinned in the SDK (private key outside the repo, `~/.gpubnb/root-signing.json`). Wire formats are normative in `gpubnb/PROTOCOL.md` (signed blobs are Ed25519 over DOMAIN‖raw payload bytes, no canonical JSON; HPKE DHKEM-X25519/HKDF-SHA256/ChaCha20-Poly1305; counter-nonced response frames with the request hash as AAD). `--simulate` mode (dev root checked in on purpose; listings carry a loud SIMULATED badge and are excluded from the default directory) runs the full flow without hardware, with Monero stagenet. Metering model-checked in `specs/Metering.tla`. Limitations stated up front: host can DoS after prepay, timing side channels, SEV-SNP only for now (TDX later), no marketplace cut. gpubnb.proc.io
